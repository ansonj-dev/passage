# Passage

An original prototype for a bilateral PUSD / ERC20 stablecoin swap using paired SHA-256 hash locks. Targets BCH Chipnet and Sepolia or an EVM local chain. This does not connect to existing bridge liquidity and does not claim a completed cross-chain trade.

## Bounty readiness

**Status: prototype; not yet a qualifying bridge demonstration.** The project has contracts and preparation tools for both directions, plus a WizardConnect path for funding the BCH side with test tokens. It has not completed a funded swap, claim, or refund on either network. The PUSD and USDC labels are examples; no issuer-backed token integration is established. The public source is at [github.com/ansonj-dev/passage](https://github.com/ansonj-dev/passage); a hosted app and funded transaction evidence are still absent.

The [bounty](https://bchblaze.cash/bounties/stablecoin-bridge/) asks for stablecoins to move both into and out of BCH. The entry still needs verified test-token contracts, a counterparty and liquidity, both-direction settlement evidence, and a public demo. See the [criterion audit](../AUDIT-00-01-04.md) and [funded-demo handoff](WIZARDCONNECT-HANDOFF.md) before attempting any transaction.

### Asset choice and network boundary

ParyonUSD is the recommended first BCH asset in the bounty. Its official site publishes PUSD's **mainnet** CashToken category as `2469acc5afa4b10cb5b5c04afb89c3a3ffd61c5da9c01e26d00951cae2a02544` ([ParyonUSD token details](https://paryonusd.com/), [deployment verification](https://paryonusd.com/docs/technical/contract-verification)). Passage currently prepares and funds Chipnet contracts only; this mainnet category must not be entered as if it were a Chipnet test token. Obtain an issuer-approved test category or use an explicitly identified test CashToken before running the demo. The test token is not PUSD.

The bounty also mentions MoriaUSD, but Moria's live app currently displays a V1 contract vulnerability notice and says that version was disabled. Passage does not integrate MUSD. Do not use that token in a demo without checking the current protocol status and getting the issuer's guidance ([Moria status notice](https://app.moria.money/)).

## Run

Requires Node 24. `npm ci`, then `npm run dev`; open http://localhost:4101. `npm run compile` generates CashScript and Solidity artifacts. `npm run build` builds the browser bundle.

The UI prepares a real CashScript Chipnet contract address from public keys and a browser-generated secret. It exports **public terms only**. Closing the browser loses the secret, so save it privately before any funding. Keep it secret until both funded contracts are independently checked and confirmed. A public hash lock alone cannot prove that a counterparty funded the correct contract.

## What is implemented

- Two directions with different expiry ordering: the first-funded chain has a four-hour timeout and the second-funded chain a two-hour timeout.
- Native BCH CashScript claim and refund branches, derived token-aware addresses and a transaction-building CLI using CashScript 0.14.
- ERC20 Solidity lock, claim and refund contract, exact deposit accounting, replay-resistant IDs, reentrancy guard and events revealing a successful claim preimage.
- EVM wallet integration through the injected EIP-1193 provider, constrained to chain 31337 or Sepolia. Explicit user wallet approvals and receipts drive EVM status; the app never reports a simulated bridge completion.
- An exportable plan and a readable trade lifecycle.
- WizardConnect HD pairing and standard wallet-input signing for test-token funding of the BCH HTLC. Preparation, signing and Chipnet broadcast are separate actions; arbitrary covenant claim/refund signing remains outside this wallet adapter.

## Funded demonstration checklist

1. Choose two independently controlled BCH compressed public keys and generate terms in the UI. Agree on the full terms with a counterparty. Neither public key is a private key.
2. Compile and deploy `StableSwap.sol` with its generated bytecode and ABI. Use a standard exact-transfer ERC20 test token. No claim is made that live USDC supports this prototype.
3. Set the EVM HTLC address, token address and counterparty EVM receiving address. Inspect amounts in token base units, chain, hash and expiry before signing.
4. The first sender locks on the longer-timeout chain. Independently verify confirmed funding before the counterparty locks on the shorter-timeout chain. The UI does not automate this validation yet.
5. For BCH, save the **bch sub-object** from the exported plan as `swap.json`. Replace the explicitly marked placeholders with the verified Chipnet token category, token base units, and token-aware claim/refund addresses. Inspect `node scripts/bch.js address swap.json`, then fund that address with **one** exact token amount and at least 2,500 sats in the same UTXO. Use test tokens; do not send mainnet PUSD to Chipnet.
6. The secret owner claims the second lock. The counterparty observes the on-chain preimage, then claims the first. For BCH set `BCH_WIF` privately, and `SWAP_SECRET` to the 64 hex secret **without 0x**. Run `node scripts/bch.js claim swap.json`. It prepares the builder and stops until `BROADCAST=YES` is intentionally set. A refund uses `node scripts/bch.js refund swap.json`; it sets transaction locktime and requires the refund key.
7. If the trade aborts before disclosure, each sender refunds after its own timeout. Use the EVM lock ID from the emitted Locked event, or the BCH contract UTXO. BCH fees are conservatively fixed at 1,500 sats in this prototype; the builder applies fee limits and preserves all quoted fungible tokens.

## Trust and practical limits

Atomic swap safety depends on network liveness, monitoring, confirmation policy, sufficient timeout margins and prompt claim/refund execution. BCH claim transactions remain valid after expiry, as in conventional Bitcoin HTLCs; a late claim can race a refund. The UI does not enforce real chain observations or prevent a participant from revealing a secret too early. It cannot guarantee safety for unattended use.

No liquidity provider, quote signature, market maker, chain watcher, counterparty matching, automatic preimage extraction or WalletConnect QR integration exists yet. WizardConnect HD pairing/signing is now available for Chipnet funding only; real-wallet interoperability remains unverified. Injected EVM wallets and a BCH CLI are usable integration surfaces for this prototype. The BCH script authorizes recipient/refund keys, and the CLI preserves the token; it is not an issuer bridge or token mint/burn protocol. Fee-on-transfer and rebasing ERC20s are unsupported. Amounts shown in dollars are not price guarantees.

Needed to complete live evidence: two test wallets, Chipnet BCH and test CashTokens, a Sepolia wallet with gas and test ERC20 inventory, a deployed EVM HTLC, an agreed counterparty, transaction monitoring and a recorded successful two-way lifecycle including refunds. No private keys are bundled. Both contracts compiled and the browser production bundle built successfully; the local server started. Offline tests now exercise public-term validation, both timeout directions and deterministic CashScript contract derivation. No network transaction or full BCH/EVM VM lifecycle test was run. The entry is not submission ready until those steps and review are complete.

## Operator preflight and observations

The expanded **Testnet swap terms** panel records the exact test CashToken category/base units, token-aware BCH payout addresses, EVM chain, HTLC/token contract addresses, sender and receiver. Fill the EVM fields in **EVM wallet & contract** before preparing a plan. Share and independently verify the exported public plan. Imported plans recompute the BCH contract address before acceptance and do not import a secret.

**Check plan and timeout window** enforces Chipnet plus Sepolia/local EVM, valid token/address fields, distinct parties, at least a one-hour expiry margin and at least 30 minutes before the short timeout. Before EVM funding, the wallet network, deployed code presence, token decimals, balance, sender/token/receiver and chain timestamp are checked. When EVM is the second-funded leg, the operator must explicitly acknowledge having checked the BCH lock. This is an operator attestation, not proof of the other chain.

**Read Chipnet unspent outputs** fetches current contract UTXOs from one Electrum server. **Read EVM lock state** reads the existing lock, hash, amount, parties and timeout from the selected contract. These are read-only, user-triggered observations. They do not establish sufficient confirmation depth, verify that a deployed contract matches the compiler artifact, or prove cross-chain settlement. Inspect the contract bytecode/artifact and chain confirmations independently before any funding.

EVM claims require the agreed token, parties, hash, amount and expiry, the receiving wallet, and a matching secret. Both the EVM UI and BCH CLI block ordinary claim execution when less than 30 minutes remain. This conservative operator guard is separate from the contract's actual eligibility rules; a near-expiry recovery needs a reviewed procedure and is not automated. Refund controls check that the sender owns the lock and the relevant time has arrived; BCH consensus median time may require additional waiting beyond local clock time.

The CLI now accepts either the full public plan or its BCH sub-object. Read-only commands need no signing key: `node scripts/bch.js preflight passage-public-terms.json`, `node scripts/bch.js address passage-public-terms.json`, and `node scripts/bch.js inspect passage-public-terms.json`. Signing still requires private environment configuration on the operator's machine. No seed or WIF belongs in chat, an exported plan or source control.

Manual gates remain: verified test-token identities, a correctly deployed EVM HTLC, two independently controlled funded wallets/counterparties, reviewed bytecode and confirmation policy, successful funded claim/refund evidence, live BCH wallet interoperability and contract-spend signing support, public hosting/repository and final submission. These changes add checks and observations; they do not supply liquidity or complete a trade.

## WizardConnect Chipnet funding

Open **BCH wallet · Chipnet funding** after preparing or importing the full agreed public terms. Use a dedicated Chipnet-capable HD wallet and test tokens only. Pair by QR/URI, acknowledge wallet network selection and a usable independent refund signer, then **Prepare**, **Review & sign**, and finally **Broadcast** as separate actions. No relay session is created until pairing is clicked, no signing request is sent during preparation, and wallet requests use `broadcast:false`. The connected wallet must support the official HD protocol and CashToken input signing.

The adapter scans the first 20 receive/change addresses, selects one matching fungible-token output plus at most one BCH-only fee input, preserves excess tokens, locks exactly the quoted token amount plus 2,500 sats, and fixes the funding miner fee at 1,500 sats. It caps total selected BCH inputs at 0.01 test BCH. Change returns to the connected wallet's change index 0; this deliberately disclosed address reuse avoids calling allocation APIs absent from the published dapp package.

Signed funding must preserve every input/output/token amount, use `SIGHASH_ALL | FORKID | UTXOS` and pass local BCH VM validation before the broadcast control is enabled. Its txid is saved before sending. Unknown broadcast outcomes remain unknown; inspect independently before retrying. Public funding records can be exported, and checked signed funding can be exported separately for recovery. Private keys, swap secrets and relay credentials are never included in these exports or local records.

This adapter funds the BCH lock; it does not claim/refund the covenant, deploy the EVM lock, extract a secret or finish a bridge trade. Have a usable signer for the agreed BCH claim/refund keys before funding. Never export wallet seeds into this app to compensate for unsupported contract signing.

See [WizardConnect handoff](WIZARDCONNECT-HANDOFF.md) for official APIs checked, exact verification and remaining participant/chain steps. `npm test` currently passes 13 offline tests; `npm run smoke` checks local HTTP/API/build files without pairing, chain queries, signing or broadcasting.
